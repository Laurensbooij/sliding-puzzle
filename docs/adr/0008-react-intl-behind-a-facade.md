# react-intl, reached only through a facade

Localisation uses **react-intl**, and every consumer imports it through
`src/lib/i18n` (`@i18n`) rather than directly. Importing `react-intl` anywhere
else is a lint error — that rule is what makes this a boundary rather than a
suggestion.

Recorded twice over: react-i18next is the more popular default and someone will
ask why it was passed over, and a wrapper around a well-known library reads as
ceremony unless its purpose is written down.

## Why react-intl

ICU MessageFormat is the reason. The move counter needs plurals and Dutch
pluralises differently from English ("1 zet" / "2 zetten"); react-intl parses ICU
natively while react-i18next needs a plugin to match it. Nearly every advantage
react-i18next has — HTTP backends, language-detector plugins, sharing i18n with
non-React code — addresses a problem a client-only puzzle does not have.

## Why a facade

The facade's surface is deliberately **smaller** than react-intl's: `translate`,
`formatNumber`, `formatList`, `Message`, `I18nProvider`, `useLocale`,
`createTranslate`. A wrapper whose whole claim is "the library is swappable" has
to actually be swappable, and that is only true while the surface stays narrow.
Add a formatter when a real consumer needs one.

## Consequences

- Messages are declared with `defineMessages` re-exported from the facade.
  Verified: `@formatjs/cli` matches the callee name rather than the import
  source, so extraction still finds them.
- Message ids are explicit and namespaced, so no Babel or TS transformer is
  wired into the build and the catalogues stay readable.
- `en.json` is generated by extraction and committed; `nl.json` is written by
  hand. CI asserts extraction is a no-op and a test asserts the key sets match —
  react-intl falls back to `defaultMessage` silently, so a missing Dutch key
  would otherwise ship English text inside the Dutch UI.
- The engine holds no strings, so it never touches i18n (ADR-0001).
