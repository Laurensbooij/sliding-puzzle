# Localization conventions

English is the default locale; Dutch is supported. See
[ADR-0008](../adr/0008-react-intl-behind-a-facade.md).

**The active locale is a stored player setting**, not provider state. It lives on
`Settings` under `@settings`, alongside the display preferences, and the browser
is consulted only to seed a first visit — an explicit choice outranks it from
then on. `I18nProvider` is **controlled**: it takes a `locale` prop and holds no
state of its own, because `@settings` imports `Locale` from `@i18n` and the
provider reading `useSettings()` would close a module cycle. `LocaleProvider` in
`src/app/` joins the two, and owns the `<html lang>` sync for the same reason
`useDocumentTitle` sits there — one document, one writer.

## Never import react-intl

Everything comes from the facade at `@i18n` (lint-enforced — `react-intl` is
importable only inside `src/lib/i18n`):

- **`useTranslate()`** → `translate`, `formatNumber`, `formatList`. For strings
  that cannot be JSX: `aria-label`, `title`, document titles.
- **`<Message message={…} values={…} />`** for text rendered in JSX.
- **`createTranslate(locale?)`** for callers with no component — chiefly tests.
- **`SUPPORTED_LOCALES`**, **`LOCALE_ENDONYMS`**, **`isSupportedLocale`**,
  **`detectLocale`** for anything reasoning about the locale set itself. Read the
  current locale from `useSettings()`; there is no `useLocale`.

**Language names are endonyms** — `English`, `Nederlands` — and are static data
in `LOCALE_ENDONYMS`, never messages. A player who picked the wrong language has
to recognise their way back out of it, which a translated list would take away.

Adding a formatter to the facade is fine when a real consumer needs it. Keep the
surface smaller than react-intl's, or the library stops being swappable.

## Declaring messages

Messages live in a **`translation-messages.ts`** beside the component that uses
them, and are imported where consumed:

```ts
import { defineMessages } from '@i18n'

export const tileMessages = defineMessages({
  label: {
    id: 'tile.label',
    defaultMessage: 'Tile {number}',
    description: 'Accessible name of a tile; {number} is its 1-based position',
  },
})
```

- **Ids are explicit and namespaced** (`tile.label`), never auto-generated.
- **Always write a `description`.** It is the only context whoever translates the
  string will have.
- **Promote on the second consumer**, same ladder as everything else: a string
  used by one component stays colocated; shared strings move to the global
  `translation-messages.ts` reached at `@messages`.
- **No literal user-facing text in JSX** (lint-enforced:
  `formatjs/no-literal-string-in-jsx`).

## Catalogues

`src/lib/i18n/locales/en.json` is **generated** — run `pnpm i18n:extract` after
adding or changing a message and commit the result. `nl.json` is written by hand
in the same shape.

CI fails when extraction is not a no-op, and a spec asserts both catalogues carry
identical key sets. That spec is load-bearing: react-intl silently falls back to
`defaultMessage`, so a missing Dutch key ships English text into the Dutch UI
with no error anywhere.
